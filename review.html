Prerequisites & environment setup
Setup

Goal

Ensure the environment is ready — Coral installed, git remotes configured, skills loaded, working directory correct. A coding agent follows these steps automatically.

1. Install & load the Coral skills

The agent needs three skills. Install them first via CLI, then load them with the skill tool in each session:

Install (one-time)

$ npx skills add withcoral/skills

This installs all Coral skills from the withcoral/skills registry — including source creation, review, and general Coral querying.

After install, the skills are available at ~/.agents/skills/ with names coral, coral-create-source-spec, and coral-review-source-spec.

Load (each session / agent context)

Once installed, load them in the agent's context using the skill tool (not a CLI command):

Skill namePurpose
coralQuery live sources via MCP, run coral sql, manage sources
coral-create-source-specCreate or update a source spec YAML — manifest structure, inputs, tables, columns
coral-review-source-specReview a source for style, product fit, query ergonomics, and consistency
If skills fail to load: Run npx skills add withcoral/skills again to ensure they're installed. Without these skills, the agent lacks domain knowledge about Coral source conventions (YAML structure, review criteria, query patterns).

2. Check or install Coral CLI

First check if Coral CLI is already installed. If not, install it:

$ which coral && coral --version || echo "NOT_INSTALLED" # If installed — you'll see the version: /opt/homebrew/bin/coral coral 0.4.2+8147372 # If NOT installed — run this (one-time): $ brew install withcoral/tap/coral
After installing, verify with coral --version. You may need to restart your terminal session.

3. Auto-detect the Coral repo clone

The agent should auto-detect the withcoral/coral clone — don't assume a fixed directory name. The clone could be named anything (e.g. coral, coral-clone, or the user's own name).

# Find the coral repo by checking common locations or detecting it from context: $ ls -d */ 2>/dev/null | head -5 # look around $ git remote -v # if already inside the repo

4. Check git remote setup

Once inside the repo root, verify the fork setup. You need two remotes — origin (your fork) and upstream (withcoral/coral):

$ git remote -v origin https://github.com/<YOUR_USERNAME>/coral.git (fetch) origin https://github.com/<YOUR_USERNAME>/coral.git (push) upstream https://github.com/withcoral/coral.git (fetch) upstream https://github.com/withcoral/coral.git (push)
Missing upstream? Add it: git remote add upstream https://github.com/withcoral/coral.git
Wrong origin? Your origin should point to your fork, not the upstream repo. Fork first on GitHub, then update: git remote set-url origin https://github.com/<YOUR_USERNAME>/coral.git

5. Verify the repo root

Confirm you're inside the coral repo by checking for the sources/community/ directory:

$ ls sources/community/ blogger/ elevenlabs/ nvidia_nim/ pdf/ ...

6. Locate the PR workspace

PR contribution files (dashboard, workflow guide, notes) live in a PR workspace directory — typically coral-pr-work/ inside the repo root. This is where pr.html, review.html, and related files are kept.

$ ls coral-pr-work/ # or if using a different naming convention: $ find . -maxdepth 2 -name "pr.html" -o -name "review.html" 2>/dev/null

7. Verify forking & sync

Make sure your fork is logged in and up to date:

$ gh auth status ✓ Logged in to github.com as <YOUR_USERNAME> $ git fetch upstream $ git checkout main && git merge upstream/main
All set? You're ready to create a source. Proceed to Step 1.

Understand the source and check existing specs
Pre-flight

Goal

Verify the provider's API is suitable and no existing Coral source covers it.

Coding agent: Step 0 auto-detected the coral repo clone (it may not be named coral). If you skipped Step 0, run git remote -v inside the repo root to confirm both origin (your fork) and upstream (withcoral/coral) are configured.

Checklist

  • Identify the provider's public API documentation
  • Verify the API has a stable, documented REST or GraphQL endpoint
  • Check sources/core/ and sources/community/ for existing coverage — use ls sources/community/
  • Check if an open issue or feature request exists for this source
  • Determine auth type: none, API key (secret), OAuth, or bearer token
  • Determine backend type: HTTP API (backend: http) or local file (backend: file + format: jsonl)

Commands

# List existing community sources to check for duplicates ls sources/community/ # Check open issues for feature requests gh issue list --repo withcoral/coral --label source-request --state open

2
Set up the source directory and manifest
Creation

Goal

Create the manifest.yaml and directory structure for your source.

Directory structure

sources/community/<name>/ ├── manifest.yaml # Coral source manifest (required) ├── README.md # Documentation (required for non-trivial sources) └── scripts/ # Optional: helper scripts for file-backed sources └── <script>.py

Manifest template (HTTP-backed)

# sources/community/<name>/manifest.yaml name: <name> version: 0.1.0 dsl_version: 3 backend: http description: <Short user-facing description of what this source queries> base_url: https://api.provider.com/v1 inputs: - name: API_TOKEN description: API token from the provider dashboard kind: secret # For OAuth, add credential.methods with device-code or authorization-code flow tables: - name: <table_name> description: <What this table returns, row semantics> filters: - name: <filter_name> # required: true # if the endpoint needs it request: method: GET path: /<endpoint> # query: # URL query parameters # headers: # custom headers (API version, etc.) response: rows_path: [<path to array in response>] pagination: mode: page # or cursor, offset, page_number, none page_param: page page_start: 1 page_step: 1 page_size: default: 100 max: 1000 query_param: per_page columns: - name: <column_name> type: Utf8 # Utf8, Int64, Float64, Timestamp, Json nullable: false description: <User-facing description> # expr: # only needed if API key != column name test_queries: - SELECT * FROM <name>.<table> LIMIT 1

Key rules

  • Source name must be lowercase, stable, and match the SQL schema users will type
  • version starts at 0.1.0 for new sources; bump when user-visible behavior changes
  • description must say what users can query, not just what vendor API is wrapped
  • Credentials must use kind: secret, never kind: variable
  • Column names must be snake_case
  • Use Json type for nested objects instead of brittle flattening
  • Every table needs at least one test_queries entry
Common mistake: File-backed sources need backend: file with format: jsonl on each table, not at the source level.
Reference implementation: See sources/community/pdf/manifest.yaml for a complete approved manifest with backend: file, format: jsonl per table, synthetic sample data, and 2-table document schema.
Coding agent: Before writing the manifest, install (npx skills add withcoral/skills) and load the coral, coral-create-source-spec, and coral-review-source-spec skills (see Step 0). Without them, the agent will lack Coral-specific YAML conventions and may produce an invalid spec.
3
Create the README documentation
Docs

Goal

Write clear documentation so users can set up and query the source immediately.

README structure (follow existing sources)

# <Provider Name> (<source_name>) ## Prerequisites # - Required accounts, API keys, OAuth setup # - Software dependencies (Python version, pip packages) # - Split by feature path (basic vs advanced/OCR) ## Quick start / Setup # 1. coral source add --file sources/community/<name>/manifest.yaml # 2. Set environment variables for secrets # 3. Run example queries ## Tables # | Table | Description | Filters | # Describe each table with columns, types, and examples ## Example queries # - Common use cases with real SQL ## Notes / Limitations # - Rate limits, pagination limits, known issues ## Validation # - Live output from coral source lint and coral source test # - Table introspection output # - Column introspection output # - Live query results with sample data

Rules

  • Always include live validation output (lint, test, introspection, queries)
  • Use sanitized/synthetic sample data — never real PII or credentials
  • Do not use mutable URLs (e.g. raw.githubusercontent.com/.../main/...) — pin to repo checkout or release tag
  • Document OCR or optional deps with clear Python version requirements
  • Reference provider docs for auth setup (token type, scopes, where to get credentials)
Reference: See sources/community/pdf/README.md for a complete example of a non-trivial README. The PDF source is a file-backed source with PyMuPDF extraction, OCR support, and comprehensive validation — approved after 4 review rounds.
4
Write helper scripts (if needed)
Scripts

Goal

For file-backed sources, create converter scripts that turn raw data into JSONL.

Script requirements

  • CLI with argparse — --dir, --files, --out, --ocr etc.
  • JSONL output matching the manifest column definitions exactly
  • Must exit non-zero on conversion failures
  • Use ensure_ascii=False for JSON output to preserve non-ASCII text
  • Document Python version requirements in script comments
  • Handle edge cases: empty PDFs, encrypted files, corrupt files, missing OCR

Pattern: error handling

# DO: let exceptions propagate, track failures, exit nonzero failures = [] for pdf_path in pdfs: try: extract_pdf(pdf_path, ...) except Exception as e: print(f"Error processing {pdf_path}: {e}", file=sys.stderr) failures.append(pdf_path.name) # Write a fallback document row if failures: print(f"ERROR: {len(failures)} PDF(s) failed: {failures}", file=sys.stderr) sys.exit(1)
DO NOT swallow exceptions and return page_count: 0 — genuine failures must signal the caller.
5
Test the source locally
Testing

Goal

Validate the manifest, test connectivity, and verify all queries work with real data.

Commands

1. Lint the manifest

coral source lint manifest.yaml
Must pass. If it fails, fix errors before proceeding. Common issues: invalid backend, missing fields, wrong dsl_version.

2. Add the source

coral source add --file sources/community/<name>/manifest.yaml
Tip: Run echo "y" | coral source remove <name> && coral source add --file manifest.yaml to re-add after manifest changes to refresh column descriptions.

3. Run tests

coral source test <name> ✓ <name> connected successfully <name> (<N> tables) ├─ table1 └─ table2 Query tests N declared · N passed · 0 failed

4. Verify table introspection

coral sql "SELECT table_name, description, required_filters FROM coral.tables WHERE schema_name = '<name>' ORDER BY table_name;"

5. Verify column introspection

coral sql "SELECT column_name, data_type, is_nullable, description FROM coral.columns WHERE schema_name = '<name>' AND table_name = '<table>' ORDER BY ordinal_position;"

6. Run live queries

coral sql "SELECT * FROM <name>.<table> LIMIT 5"
All tests pass? You're ready to prepare the PR. Save the output for the README validation section.
6
Commit, push, and create the PR
PR

Goal

Push your branch and open a pull request against withcoral/coral.

Workflow

1. Set up your fork

git remote add upstream https://github.com/withcoral/coral.git git fetch upstream git checkout -b add-community-<name>-source

2. Add and commit

git add sources/community/<name>/ git commit -m "feat(sources/community/<name>): add <Name> community source"

3. Push and create PR

git push origin add-community-<name>-source gh pr create --repo withcoral/coral \ --title "feat(sources/community/<name>): add <Name> community source" \ --body "## Summary Add a <Name> community source for querying ... ## Files | File | Purpose | | --- | --- | | \`sources/community/<name>/manifest.yaml\` | Manifest | | \`sources/community/<name>/README.md\` | Documentation | | \`sources/community/<name>/scripts/...\` | Helper script | ## Tables ... ## Validation \`\`\` coral source lint manifest.yaml Manifest is valid \`\`\` \`\`\` coral source test <name> ... \`\`\` Closes #..."

PR body must include

  • Summary of what the source does
  • Files contributed table
  • Source shape (tables, columns, filters)
  • Backend type (HTTP/file) and auth info
  • Full validation output (lint + test + introspection + live queries)
  • Provider docs links
  • Closes #<issue> if applicable
Important: Update the PR body whenever the source changes — keep validation output fresh. Do NOT use raw.githubusercontent.com/.../main/... URLs in the README or manifest guide.
7
Handle reviews (cubic-dev-ai)
Reviews

Goal

Respond to automated code review from cubic-dev-ai bot.

Rules

  • NEVER reply to cubic-dev-ai bot — only fix the issues it flags
  • Read each violation carefully and determine if it's valid
  • Fix valid issues and push to the same branch
  • False positives can be ignored — cubic will re-check on next commit
  • To re-trigger cubic review after fixes, use the "Re-trigger cubic" link in its comment, or push a new commit

Common cubic issues (from experience)

IssueFix
"Missing README.md"Create a README.md (this is often a false positive if it exists — check carefully)
OCR deps out of syncCheck current PyPI requires_python and OCRmyPDF docs for exact deps
System dep vs Python package confusionLabel clearly: (system binary) vs (Python package)
Mutable URLsReplace /main/ with repo checkout or commit hash

cubic shadow auto-approve

cubic will auto-approve when all issues are resolved and no unresolved issues from previous reviews remain. If blocked, check the "unresolved issues" section in cubic's latest comment.

Remember: cubic's "unresolved issues" are tracked per-review — even if you fix everything, the old review still shows issues. Push a new commit to trigger a fresh review.

Handle reviews (jsummerfield — human)
Reviews

Goal

Respond to human code review from the Coral maintainer.

Review patterns (from experience)

CategoryWhat jsummerfield checks
Backendbackend: file + format: jsonl on each table, not source-level
PII / DataNo real personal data in README, PR body, or sample files. Use synthetic data (Acme Corp, lorem ipsum).
JSON functionsUse Coral's json_length(), not json_array_length() or SQLite/Postgres JSON functions
Error handlingScripts must exit non-zero on failure; don't swallow exceptions
Python versionCheck requires_python on PyPI for each dependency; document exact minimums
OCR prereqsSplit PyMuPDF (3.10+) vs OCRmyPDF (3.11+). List exact deps from OCRmyPDF docs.
Mutable URLsNo raw.githubusercontent.com/.../main/.... Use repo checkout or tagged URL.

Response workflow

  1. Read the review comment carefully — each finding has a severity (High/Medium/Low)
  2. Fix the issue in the source code
  3. Commit and push: git commit -m "fix(...): describe the fix" && git push
  4. Reply to the review comment on GitHub with a summary of what was fixed and validation proof

How to reply

# Reply on the PR with a structured summary gh api repos/withcoral/coral/issues/<PR#>/comments --method POST \ --field body="All issues fixed in commit <hash>: **Issue 1:** ... **Issue 2:** ... \`\`\` \$ coral source lint manifest.yaml Manifest is valid \`\`\`"
Tip: Include validation proof in every reply — lint passes, test passes, live query results. This shows the fix works.
9
Update PR body and track in dashboard
Finalize

Goal

Keep the PR body current and reflect the source's state in the dashboard.

When to update the PR body

  • After the source is reviewed and changes are made
  • When validation output changes (re-run queries and refresh)
  • When the PR is approved — clean up stale changelog sections

Update PR body via API

# Write body to a file and PATCH cat > /tmp/pr_body.json << 'EOF' {"body": "..."} EOF gh api repos/withcoral/coral/pulls/<PR#> --method PATCH \ --input /tmp/pr_body.json
Beware unicode! Use Python json.dump(payload, ensure_ascii=False) to avoid double-escaped unicode in test output. Bad: \\u2713 — Good: ✓

Update the PR dashboard

After approval, add the PR to pr.html:

  • Bump stats: Our PRs, Approved count
  • Add PR card in the Approved section
  • Update charts if needed (donut, review cycles)
  • Update header tags and filter tab counts

Case study: PDF source (#1260)
Case Study

Goal

Walk through a real end-to-end review lifecycle — the PDF community source (#1260) — to see how all the steps above play out in practice.

PR Overview

Sourcepdf — file-backed, extracts text/tables/images/links/annotations from PDFs via PyMuPDF
Filesmanifest.yaml, README.md, scripts/pdf-to-jsonl.py
Tablespages (per-page extraction), documents (per-document metadata)

ApprovedJun 15
Review cycles3 cubic-dev-ai + 4 jsummerfield = 7 total review rounds

What made this source non-trivial

  • File-backed: Most sources use backend: http. This one uses backend: file with format: jsonl — requires a converter script, synthetic data generation, and format on each table (not source-level)
  • Converter script: 400-line Python script using PyMuPDF with edge cases (encrypted PDFs, empty files, OCR fallback)
  • OCR support: Optional OCRmyPDF integration with system deps (Tesseract, Ghostscript, qpdf) — splits user setup into two tracks
  • Validation complexity: Need to verify both coral source test and script output correctness

Review lifecycle — full timeline

Round 1: Initial state (what the first submission got wrong)

The PR was submitted with several blocking issues that would have prevented it from being added at all:

IssueSeverityWhat was wrong
backend: jsonlHighCoral only accepts http, file, and mcp. JSONL is a table format under backend: file. The source couldn't even pass coral source lint.
Real PII in sample dataHighUsed a real resume PDF as sample data — personal information exposed in README and PR body.
json_array_length()MediumTable guides used json_array_length() (SQLite/Postgres function) instead of Coral's json_length().
Mutable URLsMediumConverter download URL used raw.githubusercontent.com/.../main/... — schema-drift and remote-code-execution risk.
OCR prereqs understatedMediumREADME presented OCR as pip install ocrmypdf — missing Tesseract, Ghostscript, qpdf system deps.
Converter path brokenMediumRepo checkout instructions had wrong script path (python pdf-to-jsonl.py from repo root, but script lives in sources/community/pdf/scripts/).
Resource leakP1doc.close() and shutil.rmtree() not in finally block — exceptions during extraction would leak temp files and PDF handles.
Dict vs tuple indexingP1get_page_labels() returns dicts, not tuples — positional label[0], label[1] would raise KeyError.
Unused run_ocr functionP2Dead code duplicating OCR behavior inline.
Output dir not createdP2--out-documents fails when targeting a new directory — no mkdir call.

Round 2: Response to jsummerfield round 1

Changes requested: High: backend, High: PII, Medium: converter path, Medium: OCR prereqs, Low: URL

Fix: Commit 9a4e3f0 — switched to backend: file + format: jsonl, replaced PII with synthetic sample_report.pdf (Acme Corp, lorem ipsum), split standalone vs repo-checkout install paths, documented full OCR deps, fixed URL to withcoral.com/docs.

Round 3: cubic-dev-ai re-review + jsummerfield round 2

cubic found: Guide removed script download step, leaving incomplete instructions for users seeing guide via coral describe.

jsummerfield found: Still using json_array_length() instead of json_length() in table guides — the fix in 9a4e3f0 missed some spots.

Fix: Commits 9707c34 + e31393e — added curl download step back to manifest guide, replaced all json_array_length() with json_length(), validated with live queries showing json_length(links) > 0 output.

Round 4: cubic-dev-ai round 3

cubic found:

  • Failure detection can't distinguish a valid zero-page PDF from a conversion error
  • Python prerequisite bumped to 3.9+ without justification — PyMuPDF actually requires 3.10+

Fix: Commit 8002386 — made extract_pdf() propagate exceptions, added explicit failures list tracking, corrected Python to 3.10+ (3.11+ for OCR).

Round 5: cubic-dev-ai round 4

cubic found:

  • Removed live content proof sections (TOC, links) from README, reducing documentation value
  • Example queries still reference old file names (resume.pdf, report.pdf) instead of sample_report.pdf

Fix: Commits 21fe937 + c585b73 — restored TOC/links proof sections, renamed all examples to use sample_report.pdf.

Round 6: jsummerfield round 3

Changes requested: OCR setup requirements still understated — README let users start with Python 3.10 for PyMuPDF then present OCR as a simple pip install, but actual OCRmyPDF needs Tesseract 5.x, Ghostscript 9.55+, qpdf. Also, the converter distribution path still needed work.

Fix: Commit 00021f0 — split prerequisites into two clear sections (For plain-text PDFs: Python 3.10+ + PyMuPDF vs For scanned PDFs (OCR): Python 3.11+ + OCRmyPDF + full system deps). Removed standalone curl download; only repo checkout path documented.

Round 7: jsummerfield round 4

Changes requested: pypdfium2 mislabeled as system dependency instead of Python package in OCR deps list.

Fix: Commit d337112 — added labels: Ghostscript 9.54+ (system binary) vs pypdfium2 (Python package).

Round 8: jsummerfield round 5 — Approved

jsummerfield re-checked with coral source lint, make lint-sources, and git diff --check. All green. Approved with status: approved.

Key takeaway: It took 7 review rounds and 10+ commits to get this right. Every round addressed real issues — no trivial back-and-forth. The most impactful fixes were: fixing the backend field (source wouldn't load), removing PII (privacy), switching to json_length() (query correctness), and getting OCR deps right (user experience).
