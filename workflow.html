Coral Source PRs — Agent Workflow Reference

✓ Copied to clipboard

Goal: Any coding agent reading this should be able to create a Coral community source PR from scratch. This file explains the workflow, directory structure, skills to load, and patterns from 20 past PRs.

Directory Structure

~/coral/
  |
  coral-pr-work/                  # FORK CLONE of FiscalMindset/coral
  |   origin → FiscalMindset/coral
  |   upstream → withcoral/coral
  |   coral CLI already installed
  |
  |── sources/community/<source>/   # ONLY 2 FILES PER PR:
  |   ├── manifest.yaml              # Source spec
  |   └── README.md                  # Documentation
  |
  output_proof/                     # LOCAL ONLY — .env with API keys

Branch naming

add-<name>--source           # e.g. add-stream-video-source

Start a new source

Auto-detect the coral repo clone first — it may not be named coral. Look for sources/community/ or run git remote -v to confirm.

cd <repo-root>
git switch main
git fetch upstream
git merge --ff-only upstream/main
git checkout -b add-<source>-source

API Keys (.env)

Location: ~/coral/output_proof/.env
Format:   <PROVIDER>_API_KEY=xxx

Examples:
  DEEPGRAM_API_KEY=your_deepgram_key
  STREAM_API_KEY=your_stream_key
  STREAM_SERVER_TOKEN=your_stream_token

The agent needs to export these before running coral commands.
Never commit .env or any real key values.

PR title format

feat(sources/community/<source_name>): add <Provider> community source

Workflow (Step by Step)

Phase 0: Prerequisites

Check Coral CLI:

which coral && coral --version || brew install withcoral/tap/coral

Phase 1: Install & Load Skills

Install (one-time):

npx skills add withcoral/skills

Then load (each session):

Skill: coral-create-source-spec
Skill: coral-review-source-spec
Skill: coral

The create skill has detailed instructions for building manifest.yaml. The review skill has the review checklist. The coral skill provides live query and source management via MCP.

Phase 2: Analyze the API

  1. Read the provider's API docs
  2. Determine: base URL, auth method (API key, Bearer, OAuth, etc.), required headers, response JSON shape, pagination style (if any), rate limits, deprecated fields
  3. Decide which endpoints to model as tables — each table maps to one API endpoint
  4. Decide columns based on the API response JSON paths
  5. Decide required filters (filters the API requires vs optional ones)
  6. Decide pagination (does the API support it? what mode? cursor vs offset vs page?)
  7. Check if IDs contain /, :, or other path-sensitive characters

Key: Everything depends on the API. No hard rules about pagination, page_size, filters, columns — they all depend on what the provider's API actually does.

Phase 3: Create manifest.yaml

Located at sources/community/<source>/manifest.yaml

Follow the coral-create-source-spec skill instructions. Typical sections:

  • name, version, dsl_version
  • backend (usually http)
  • base_url
  • inputs — secrets (API keys) and variables (non-secret config)
  • auth — header auth, query param auth, etc.
  • tables — each with method, path, filters, columns, rows_path, pagination (if applicable)
  • test_queries — safe, source-independent SQL tests

Phase 4: Write README.md

Located at sources/community/<source>/README.md

Sections: Summary, Authentication, Live Request Costs (if billable), Provider Docs (links), Source Shape, Tables (with columns), Validation (lint + add + test + live SQL output), Scope & Limitations.

Text proof only. Redact real identifiers. No AI wording, no local paths, no WSL.

Phase 5: Validate Locally

First export API keys from output_proof/.env:

export $(grep -v '^\s*#' ~/coral/output_proof/.env | xargs)

Run validation. Capture output for README and PR body. Every table needs live SQL proof, not just the test queries.

# 1. Lint
coral source lint sources/community/<source>/manifest.yaml

# 2. Add source (shows tables + test query results)
coral source add --file sources/community/<source>/manifest.yaml

# 3. Source test
coral source test <source>

# 4. Table introspection
coral sql "SELECT table_name FROM coral.tables WHERE schema_name = '<source>' ORDER BY table_name"

# 5. Column introspection
coral sql "SELECT table_name, column_name, data_type FROM coral.columns WHERE schema_name = '<source>' ORDER BY table_name, ordinal_position"

# 6. Inputs introspection
coral sql "SELECT key, kind, required FROM coral.inputs WHERE schema_name = '<source>' ORDER BY key"

# 7. Live proof for EACH table — select real columns with LIMIT
coral sql "SELECT col1, col2 FROM <source>.<table1> LIMIT 3"
coral sql "SELECT col1, col2 FROM <source>.<table2> WHERE required_filter = 'val' LIMIT 3"

For README/PR body, present each command followed by its output in a code block. Redact identifiers but keep column shapes real. Example format:

```bash
$ coral source lint sources/community/<source>/manifest.yaml
Manifest is valid
```

```bash
$ coral source add --file sources/community/<source>/manifest.yaml
Added source <source>

  ✓ <source> connected successfully

    <source> (N tables)
    ├─ table1
    └─ table2
    Query tests
    N declared · N passed · 0 failed

    ✓ SELECT ...
      N rows
```

```bash
$ coral sql "SELECT col1, col2 FROM <source>.<table1> LIMIT 3"
+---------+---------+
| col1    | col2    |
+---------+---------+
| val1    | val2    |
| val3    | val4    |
+---------+---------+
```

Phase 6: Create PR

git add sources/community/<source>/
git commit -m "feat(sources/community): add <Provider> source"
git push origin add-<source>-source
# Create PR via GitHub

PR body: Summary, Why this source, Provider docs, Source shape (tables), Source scope, Validation output (lint + add + test + live SQL), Closes #issue.

Phase 7: Respond to Review

  • Do NOT reply to cubic-dev-ai[bot] — just fix issues silently
  • DO reply to jsummerfield (human) with commit SHA + what changed + fresh validation proof

Case Study: PDF Source (#1260)

A real end-to-end review lifecycle for a file-backed source. PR #1260 went through 7 review rounds (3 cubic-dev-ai + 4 jsummerfield) and 10+ commits. Key lessons:

  • backend: jsonl is invalid — use backend: file + format: jsonl on each table
  • Synthetic data only — real resume PII in samples was a High blocker
  • Coral JSON functions — use json_length(), never json_array_length()
  • Mutable URLs — never /main/ in download links; use repo checkout
  • Split deps by feature — basic (3.10 + PyMuPDF) vs OCR (3.11 + OCRmyPDF + Tesseract + Ghostscript + qpdf)
  • Label system vs Python deps — e.g. Ghostscript (system binary) vs pypdfium2 (Python package)
  • Keep validation proof — never remove live query output from README

See Step 11 in review.html for the full breakdown.

Rules

  • Only 2 files per PR: manifest.yaml + README.md in sources/community/<source>/
  • Check Coral CLI: which coral && coral --version; install if missing: brew install withcoral/tap/coral
  • Install skills: npx skills add withcoral/skills (one-time); load via skill tool each session
  • backend must be http, file, or mcp — never jsonl
  • Use synthetic sample data only — no real PII, real names, or real emails
  • Use Coral JSON functions: json_length(), never json_array_length()
  • No AI/Codex/ChatGPT wording anywhere in public PRs
  • No WSL, local paths, or real API keys in public text
  • Redact identifiers: your-app, user_abc123, call_abc123
  • Never commit .env or real API keys
  • Do NOT reply to cubic-dev-ai[bot]; DO reply to jsummerfield
  • Live tables require a positive bound (max_tokens etc.)
  • Document paid API costs near Authentication section
